# Review of ADR-0019 (WAL mode), fresh Claude session

Reviewer: a fresh Claude agent, one of three independent reviewers, 2026-10-22. Prompt: [prompts/adr-0019-wal-round-1.md](prompts/adr-0019-wal-round-1.md).

Scope: `docs/adr/0019-sqlite-wal-mode.md` against `leafi/core/storage.py`, the openers (`leafi/runner.py`, `leafi/ops/supervisor.py`, `leafi/cli.py`), `tests/test_storage.py`, ADR-0017 §7.3, ADR-0018 §7.2 and SQLite's WAL documentation. WAL itself and keeping SQLite are not argued.

Probes: two throwaway scripts on temp files under the session scratchpad (never `data/leafi.db`), run with `.venv\Scripts\python` — Python 3.12.10, SQLite 3.49.1, Windows 11. Results are quoted as "probe N" below.

## Findings

There is **one High** finding.

### High

**H1 — §1: the fallback when the switch cannot happen is wrong. The pragma raises an error; it does not return a different mode.** §1 says: "if the pragma returns anything other than `wal` (another process holds a lock at that moment), the open continues in the current mode and logs one warning". On this machine, `PRAGMA journal_mode = WAL` on a rollback-mode file raises `sqlite3.OperationalError: database is locked` while another connection holds a read transaction (probe 2: immediately with `busy_timeout` 0; after 1.15 s with `busy_timeout` 1000) or a write transaction (probe 3). It also raises when another connection only has a half-read cursor in autocommit mode (probe 2b). The only non-`wal` return value seen was `memory`, for `:memory:`. A `Store.__init__` written to the ADR checks the return value and never catches the exception, so the open fails.
- *Failing scenario:* the owner has `leafi.db` open in DB Browser for SQLite (or the `sqlite3` shell) with a read transaction pending, then upgrades Leafi. Every opener — supervisor, `python -m leafi study`, `leafi alert` from keep.ps1 — waits 5 s and then dies in `Store.__init__` with a traceback. keep.ps1 restarts the supervisor into the same crash until the other tool lets go. The ADR promises one warning and a normal open instead. Before WAL, in rollback mode, the same reader only made writes fail.
- §1 also undersells the condition. The switch needs a moment with no other connection *reading or writing*, not only "no other connection writing".
- On an already-WAL file the pragma is a true no-op: it returns `wal` even while another connection holds a read, write or EXCLUSIVE transaction (probe 13). The hazard therefore exists only during the one-time switch, which is exactly when nobody is watching.
- *Fix:* run the pragma in `try/except sqlite3.OperationalError`, log one warning and continue in rollback mode (as the ADR intends). Add a Confirmation test where a second connection holds `BEGIN; SELECT …` while `Store(path)` opens a rollback-mode file; it must open and warn, not raise. Write the condition as "no other connection holds any lock".

### Medium

**M1 — §1 "A new empty file is created in WAL directly", hand-executing two processes opening a brand-new file: `migrate()` races and one opener crashes.** This race already exists in rollback mode, but this ADR is where the open path is redesigned, and WAL widens the window. `Store.migrate()` reads `PRAGMA user_version` outside its transaction and only then runs `BEGIN IMMEDIATE`.
- Probe 4: both connections switch to WAL fine (probe 4b: even while the other is reading) and both read version 0. c1 migrates and commits. c2's `BEGIN IMMEDIATE` waits, then runs step 1 again and fails with `table books already exists`.
- In WAL, a reader sees the pre-migration snapshot for the whole of c1's migration, instead of being blocked during c1's commit. Each step is its own transaction, so a second opener can also see version 1–3 part-way.
- ADR-0018 §7.2's shared `.users` lock does not prevent this, because every normal opener takes it shared.
- *Failing scenario:* a first install or a deleted `data/`: the supervisor starts at logon while keep.ps1 runs `leafi alert` at the same moment, and one of them exits with an `OperationalError`.
- *Fix:* inside `migrate()`, re-read `user_version` after `BEGIN IMMEDIATE` and skip the steps already applied. Add a regression test: two `Store` objects on one new path with the interleaving above.

**M2 — §2 "the last connection to close checkpoints and removes the `-wal` file", and Consequences "Two transient files": in production the files are permanent, and `-wal` never shrinks.**
- No production opener calls `Store.close()`: `runner.run_study`, `supervisor.run` (its `finally` closes the lock but not the store), and `cmd_export`, `cmd_forget` and `cmd_alert`.
- The supervisor runs from logon and is ended by keep.ps1 or logoff without a close, so there is almost never a "last connection". A crashed or killed process leaves `-wal` and `-shm` behind (probe 7).
- `journal_size_limit` is not set, so after a checkpoint `-wal` stays at its high-water size (probe 12: 4.36 MB still on disk after a full PASSIVE checkpoint and a later small commit).
- ADR-0018 §7.2's migration 5 rebuilds every table in one transaction, so it writes the whole database into `-wal`. From then on `-wal` stays at least as large as the database.
- *Consequence for §4:* "copying the database file by hand becomes unsafe while Leafi runs" is too narrow. A file copy is unsafe whenever `leafi.db-wal` exists, which includes after the supervisor was killed and Leafi looks stopped. Probe 7: a plain copy of `leafi.db` after a crash is missing the committed row 42.
- *Fix:* set `PRAGMA journal_size_limit` (for example 4 MiB) in `Store.__init__`. Close the store in `finally` in the runner, the CLI commands and the supervisor. Reword §4/Consequences: "never copy `leafi.db` while a `leafi.db-wal` file exists; use `VACUUM INTO`". Consider a `leafi backup` command, since §4 asks for a mechanism the owner currently has no button for.

**M3 — Consequences and Confirmation: where a `COMMIT` can still fail is misstated, so the test plan protects the wrong path.** Consequences says "a `COMMIT` can still fail on a writer–writer collision, which the existing rollback … covers".
- In WAL with `BEGIN IMMEDIATE`, a writer–writer collision fails at `BEGIN IMMEDIATE`, not at `COMMIT`: the write lock is held from `BEGIN`. Probe 11: a reader can no longer fail a `COMMIT`.
- In WAL, the new busy failure SQLite really has is `SQLITE_BUSY_SNAPSHOT`. A connection that begins with plain `BEGIN`, reads, and then writes after another connection committed fails at once, and `busy_timeout` does not help (probe 5).
- Today no code uses a deferred `BEGIN` (grep of `leafi/`), so nothing breaks now. But nothing records the rule, and ADR-0017 §7.3's retry wording assumes that waiting helps.
- The Confirmation plan keeps the failed-`COMMIT` test alive only through a test-only `journal_mode` argument on the production `Store`. That tests a mode production never runs.
- *Fix:* state that busy errors in WAL come from `BEGIN IMMEDIATE`, plus `SQLITE_BUSY_SNAPSHOT` for any deferred read-then-write, and that every write transaction must stay `BEGIN IMMEDIATE`. Keep the rollback-on-failed-`COMMIT` code as defence, but drive its test by making `COMMIT` fail another way, or record why a production parameter exists only for a test.

### Low

**L1 — §2 "`busy_timeout` stays 5000 ms" contradicts ADR-0017 §7.3,** which gives the study process 250 ms. With 250 ms, the H1 switch fails far more easily in the study process. Name ADR-0017 §7.3's value, or say which one wins.

**L2 — §1 with `:memory:`:** the pragma returns `memory` (probe 9), so the §1 rule "anything other than `wal` → warning" logs a warning on every in-memory store. Exempt `:memory:`; `Store.__init__` already special-cases it for `mkdir`.

**L3 — §1 ordering against ADR-0018 §7.2:** the WAL switch writes the file header, so it must run after the opener takes the shared `.users` lock and before `migrate()`. Otherwise it can run while `leafi migrate` holds the exclusive lock. State the order: shared lock → `busy_timeout` → `journal_mode` → `migrate`.

**L4 — §4 restore:** restoring by replacing `leafi.db` while a stale `leafi.db-wal` from the old file still sits beside it lets SQLite replay old frames onto the new file. §4 already requires the backup API for restores. Add one sentence: anyone who replaces or deletes `leafi.db` by hand must also remove `-wal` and `-shm`, and only while no process has the file open.

## Hand-executions with no new finding

- **First open of the existing rollback file while the supervisor holds an idle connection (probe 1):** the switch succeeds (`wal`). The supervisor's older connection follows WAL on its next statement and writes normally. It fails only while a lock is held (H1).
- **A reader in an open read transaction while the study process commits (probe 5):** the `COMMIT` succeeds with `busy_timeout` 0. The reader keeps its snapshot. `wal_checkpoint(TRUNCATE)` reports busy until the reader ends, then completes. As designed.
- **The last connection closing (probe 6):** `-wal` and `-shm` stay while any connection is open and are deleted when the last one closes. That is true, but rarely reached in production (M2).
- **A crash with a non-empty `-wal` (probe 7):** the next read-write opener recovers row 42 and removes the files on close. A `mode=ro` opener also sees row 42, with or without `-shm`, when the directory is writable.
- **Tests opening many `Store` objects on tmp files (probe 8):** on Windows, deleting `-wal`, `-shm` or `leafi.db` while a connection is open fails with WinError 32. A rollback-mode file is just as undeletable while open, so this is not new. A `Store` dropped by garbage collection closes and removes `-wal`/`-shm` (probe 8b). pytest keeps and later prunes `tmp_path` folders without failing a run. No test lists the tmp directory.
- **A `mode=ro` reader (probe 7):** works; §5 is accurate for this PC.
- **Switching back to `delete` while another connection is open (probe 10):** raises `database is locked`. This matters only if a test ever opens a rollback-mode store on a file that is already WAL; on fresh tmp files it is fine.
