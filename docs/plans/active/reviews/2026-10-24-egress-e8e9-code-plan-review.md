Reviewer: a fresh Claude session (did not write the design), walking `code-plan-review`'s catalog (G4, B1/B2, C2, H3, H7, I1/I2, J not touched). Read: the design rev 1 (E8, E9, with E6/E7/E10/E11 where E8–E9 depend on them), ADR-0021, the research note, ADR-0018 §1, ADR-0019 §5–§8, the prompt file; code: `leafi/core/storage.py` (`SCHEMA_V5`, `SCHEMA`, `_V5_COPY`, `migrate_file`, `_step`, `rebuild`, `Store._open_schema`, backup and restore), `leafi/core/learner_store.py`, `leafi/study/records.py`, `leafi/study/brain/call.py`, `leafi/study/harness/{rows,busy}.py`, `leafi/study/cards.py`, `tests/test_architecture.py`, `tests/test_migration_6.py`; grep across `leafi/` and `tests/` for every reader and writer of the dropped columns. I did not read the other reviewers' files.

The model, restated: one household file; `migrate_file` (exclusive `.users` lock, auto-backup, one transaction per step) is the only migrator, and `Store` refuses any file that is not at `SCHEMA_VERSION`. `forget --learner N` marks N, deletes in batches, then deletes the row. Today the fence and the purge read the per-row `*_source_learners`; E9 switches both to the row's owning learner.

## Findings

**1. High — step 6 targets the live `SCHEMA`, so the chain 5→6→7 breaks (G4.3, H3.2).** Where: E8 says "`SCHEMA` edited to match". Where it fails: `migrate_file` runs `_step(conn, 6, SCHEMA, …)` (storage.py:822). Once `SCHEMA` has no provenance columns, a version-5 file (or a version-4 one going through 5) is rebuilt straight into the v7 shape and stamped 6. Step 7's `DROP COLUMN` then fails with "no such column", rolls back, and leaves the file at version 6 in a shape no step can migrate. `test_migration_5`/`_6` (which compare against a fresh file and assert `SCHEMA_VERSION == 6`) go red too. Fix: freeze `SCHEMA_V6 = SCHEMA` before the v7 edits, the same way `SCHEMA_V5` is frozen. Step 6 targets `SCHEMA_V6`, and a new `if version == 6:` branch runs step 7. Add to E11: update `test_migration_6` and keep a 4→7 and 5→7 path test.

**2. High — the fence disappears for `activities`, `utterances` and `brain_calls` (B1.5, G4.1, C2.2).** Where: E9's fence bullet ("its `learner_id`, or its session's learner … a conditional insert"), with no SQL given. Where it fails: `insert_named` builds its ids only from `stated_sources(cols)` (learner_store.py:107). Once the columns are gone, `ids == []`, and `_fence([])` evaluates `COUNT(*) … IN () = 0`, which is always true, so every insert passes. `PROVENANCE_TABLES` is derived from the dropped-column list, and `test_architecture`'s `fenced = DIRECT | PROVENANCE_TABLES` then shrinks to `DIRECT`. Plain `INSERT INTO brain_calls` anywhere would pass the architecture test. The same gap opens as early as commit 3 if writers start filling the columns with `system`/`[]`. Fix: an explicit `SESSION_OWNED = {activities, utterances, brain_calls}` (state whether `cycles`, `page_reads`, `observations`, `miscues`, `practices`, `egress_log` join it or why not). `insert_named` takes the owner from `cols["session_id"]` inside the statement: `… WHERE EXISTS(SELECT 1 FROM reading_sessions rs JOIN learners l ON l.id = rs.learner_id WHERE rs.id = ? AND l.forgetting = 0)`. A missing session or learner then also refuses, instead of raising an FK `IntegrityError`. `test_architecture` uses the explicit set. Regression tests: a `brain_calls` insert for a forgetting learner's session is refused; for a session adopted away from a guest it is accepted.

**3. High — the stated cost is wrong about where copies live (I2.3, decision for the owner).** Where: E9 "Accepted cost … the stored copy itself stays local", and ADR-0021 Consequences. Hand-execution: forget N, where M has a card whose explanation quoted N (`cards.stored_text` joins those sources on purpose). Today `_purge_derived` deletes M's outbox row and `_remember_notes` lists its `anki_note_id`, so the household removes the note from Anki and AnkiWeb. Under E9 the row stays, nothing is listed, and the synced card stays in AnkiWeb, a cloud copy, with no notice. Other things also survive and are not named: M's utterance text, `brain_calls` payload/response, activity outcome/assessment and encounter explanations that quoted N. Nothing in `forget`'s output tells the parent any of this. Fix: correct the sentence in E9 and ADR-0021, and print the cost in `leafi forget`'s report. Owner to decide: whether M's Anki notes still need listing (no column can find them any more, so the honest answer may be "no, and say so").

**4. Medium — the name protection E9 relies on moves only the display name (C2.1, I1.1).** Where: E9 "N's names still move into `household_terms`". Where it fails: `forget_learner` inserts only `row["display_name"]` (records.py:278). ADR-0018 §1 says "display name and other identifying names", and `pseudonym.py` protects the alias as part of `learner:<id>`. After the row is deleted, N's alias in M's surviving notes or utterances is on no list and depends on the detector alone. That mattered less while the purge removed those rows; now it is the only cover. Fix: move the alias (and any other listed name) in the same statement, and add a test.

**5. Medium — `VACUUM` has no owner, and the canary test as written cannot fail (H7.1, B4.1).** Where: E8 "After: one `VACUUM` (with `secure_delete` already on)", and rollout step 3. Where it fails: no code or command runs it. `migrate_file`'s connection is a raw `sqlite3.connect`, without `secure_delete` (that pragma is set per connection in `Store.__init__`). Under WAL, `VACUUM`'s output goes into `-wal`, and the old pages stay in the main file until a TRUNCATE checkpoint. The class values (`'learner'`, `'page'`) and lists like `'[1]'` occur in other columns, so "canary absent" needs a distinctive value in a `*_source_learners` column (no CHECK there, e.g. `'[987654321]'`), checked in both `leafi.db` and `-wal`, as ADR-0019's forget test does. Fix: `migrate_file` runs `VACUUM` and then `wal_checkpoint(TRUNCATE)` after step 7's commit, outside the transaction, still holding the exclusive lock (no other connection can exist). It reports a failure and leaves the file valid at 7.

**6. Medium — E8 describes a runner the code doesn't have, and uses two mechanisms where one exists (H3.1, H7.2, I1).** Where: "one transaction under `migrate()`'s `BEGIN IMMEDIATE`" and rollout "the first open migrates to 7". In the code, `Store._open_schema` raises `NeedsMigration` for 6. The owner must run `python -m leafi migrate`, which takes its own `leafi-v6-*.db` backup, so the manual `leafi backup` makes a second v6 copy and uses one of `BACKUPS_KEPT = 3`. `_step` is a rebuild-differ: given the v7 `SCHEMA`, it would drop the columns by rebuilding, using machinery migrations 5–6 already proved. If `DROP COLUMN` is used instead, `_step`'s differ still rebuilds any table whose normalised DDL differs from the hand-edited `SCHEMA`. The research's S2 finding doesn't mention `_step`. Fix: choose one (recommended: `_step(conn, 7, SCHEMA, {})`, no new mechanism; or DROP COLUMN in a `before` hook with the differ as a check). Add `schema_of(migrated) == schema_of(fresh)` to `test_migration_7`, as tests 5 and 6 have. Correct the rollout to `leafi migrate`.

**7. Medium — commit order leaves NOT NULL columns with no writer value (G4.3, I1).** Where: E10's commits 3 then 4. Commit 3 deletes `leafi/core/provenance.py`, `join` and `of_output`, but `learner_store` imports `PARENT_SOURCE`, and `call._row`, `rows.start/finish_activity`, `activities.py:56/604`, `knowledge.py:53` and `cards.stored_text` fill 20 `NOT NULL` no-default columns that live until commit 4. Fix: either keep `learner_store.prov` writing a constant `('system', '[]')` through one helper in commit 3 (and say the fence and purge are inert until commit 4), or move the storage writers' changes into commit 4. Commit 4's test list must name `tests/seed.py`, `test_forget`, `test_learner_store`, `test_migration_5/6`, `test_open_db`, `test_brain_call`, `test_activity_status` and the others among the 21 test files that reference the columns or `SCHEMA_VERSION`.

**8. Medium — a refused audit row escapes the Brain call (A3.9, B4.1).** Where: E9 "the audit write logs and drops them". In the code, `call._insert` catches `LearnerUnavailable` and writes `_withheld(row)`, which E6 deletes. Under the owner fence that fallback would be refused too. `busy.retry` re-raises anything that isn't busy, so `write_audit` raises into the call, and `flush_audit` raises at `finalize` with the row never popped from `pending_audit`. Fix: `_insert` catches, logs and returns, so the row is popped. Test: `finalize` with a forgetting owner completes.

**9. Low — removing the final rescan leaves no sweep before the row delete (B1.1).** Where: E9 "`_purge_derived` and its rescan … go". A row written between batches by a writer outside the fence (`egress_log` uses a plain insert keyed on `learner_id`) makes the final `DELETE FROM learners` fail on the FK. That is safe, since a rerun resumes, but it is noisy. Fix: the last transaction repeats the by-owner deletes (direct tables, `egress_log`) before deleting the row.

**10. Low — stores outside the DB are said to be listed but are not reached (I2.3).** E9 says "as ADR-0018 §1 already lists", but `forget_learner` reaches only `data/learners/<id>/`. E7's "delete the whole `cache/tts/`", `data/evals/decisions/` and DEBUG logs are not in E9's steps or E11's `test_forget`. Fix: list each store and its step (or "none exists yet"), and test the TTS-cache deletion.

**11. Low — leftover second fence subjects (I2.1).** `insert(…, sources=…)` and `update_named`'s owner read in a separate statement (learner_store.py:129) remain. Fix: drop `sources`, and read the owner inside the UPDATE's own `WHERE` through the session join.

**12. Low — renumbering and restores are not propagated (I1).** "Migration 7" still means `item_status_events` in `2026-10-23-m7-brain-design.md` (4×), `2026-10-24-practice-planning-design.md` and `2026-10-22-ai-led-study.md`, and E12 doesn't list them. Restore: a v6 backup refuses to open until `leafi migrate` runs again, and a pre-forget backup brings N back (ADR-0019 §8). E8's rollout should say both. The dropped values themselves (class names, id lists) are low-sensitivity, so the backups keeping them is acceptable once stated.

## Sound

- `DROP COLUMN` is legal on all 20 columns: each has only its own column CHECK, and no index, partial index, FK, trigger or view names them. The six `_BUMP` triggers touch only `learners` and `household_terms`. The list (7 tables, 20 columns) matches `PROVENANCE` and every provenance column in `SCHEMA`.
- Concurrency of the migration: the exclusive `.users` lock excludes every `Store`. A crash mid-step rolls back that step's one transaction.
- `forget --learner` by `learner_id` and by `session_id` reaches every table ADR-0018 §1 lists. M's rows attached to N's sessions (notes, encounters, retrieval events by activity) go with them. `forget --session` and `--book` don't read the dropped columns and stay complete.
- Fencing by the session's current owner (via the join) is more correct after `adopt_session` than the stamped sources were.
- No runtime reader outside E10's list (no `doctor`, `report` or export) reads the dropped columns.
