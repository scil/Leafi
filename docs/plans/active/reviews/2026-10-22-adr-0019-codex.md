**One High finding, six Medium findings, and one Low finding.** WAL’s normal reader/writer behavior fits the goal; the gaps are runtime compatibility, startup races, connection ownership, and recovery.

1. **High — Decision / §2: the installed SQLite predates a WAL corruption fix.**  
   The project venv reports **SQLite 3.49.1**. SQLite documents a rare WAL-reset race involving concurrent writing/checkpointing connections: a checkpoint overlaps another connection resetting the WAL, and subsequent checkpointing can omit committed content. The supervisor/study arrangement supplies concurrent connections; this is a possible failure, not an observed reproduction. Require a runtime containing the fix before enabling WAL—3.51.3 or later, or a documented patched backport. High reflects potential system-of-record corruption, despite the low probability. [SQLite’s bug description](https://www.sqlite.org/wal.html#walresetbug), [3.51.3 release notes](https://www.sqlite.org/releaselog/3_51_3.html).

2. **Medium — [§1, Setting it](/E:/GitHub/scil/Leafi/docs/adr/0019-sqlite-wal-mode.md:15): the conversion failure path is incomplete.**  
   Hand-execution: the supervisor already has a rollback-mode connection. If it is idle with no transaction or active statement, conversion can succeed; merely having the connection open does not prohibit it. If it holds a read transaction, however, the new opener cannot obtain the **exclusive lock** required for conversion—even with no writer. SQLite documents that requirement in its [WAL locking protocol](https://www.sqlite.org/walformat.html#operations_that_require_locks_and_which_locks_those_operations_use).

   Lock contention can raise `sqlite3.OperationalError`/`SQLITE_BUSY`; checking only whether the pragma returns `wal` misses that path. The named openers do not catch constructor failures. Define handling for busy exceptions separately from unsupported-mode returns and genuine I/O errors, and close the connection on failed initialization. If continuing in rollback mode is intentional, the promised concurrency improvement remains conditional until a later conversion succeeds.

3. **Medium — §1 / Confirmation: simultaneous first opens race in `migrate()`.**  
   In [storage.py](/E:/GitHub/scil/Leafi/leafi/core/storage.py:162), `user_version` is read **before** `BEGIN IMMEDIATE`.

   Hand-execution, even assuming both WAL pragmas succeed: A and B both read version 0; A acquires the write lock, creates migration 1’s tables, and commits; B then acquires the lock and executes its already-selected migration 1. `CREATE TABLE books` fails because the table exists. Waiting for the writer does not refresh B’s migration decision.

   This is a pre-existing startup race that the proposed change leaves exposed. Version selection and migration execution must share serialization, with the version re-read under that protection. Confirmation needs a coordinated two-opener test; sequential reopening proves something different. ADR-0018’s proposed shared lifetime locks do not themselves serialize two ordinary new-file openers.

4. **Medium — [§2 / Confirmation](/E:/GitHub/scil/Leafi/docs/adr/0019-sqlite-wal-mode.md:16): clean closure has no owner.**  
   `Store.close()` exists, but [runner.py](/E:/GitHub/scil/Leafi/leafi/runner.py:33), [supervisor.py](/E:/GitHub/scil/Leafi/leafi/ops/supervisor.py:591), and the three CLI openers never call it. [Storage tests](/E:/GitHub/scil/Leafi/tests/test_storage.py:58) similarly leave Stores unclosed, including an anonymous second Store.

   Hand-execution: many temporary Stores remain live, or await garbage collection, when cleanup attempts to remove their files. On Windows, open database/sidecar handles can prevent deletion. Surviving Stores also mean the supposed “last connection” has not actually closed.

   Give every opener and fixture deterministic teardown, including exception paths and failed construction. A clean final writable connection normally checkpoints and removes both sidecars; a final read-only connection does not perform that cleanup. [SQLite file lifecycles](https://www.sqlite.org/walformat.html#file_lifecycles).

5. **Medium — §2 / Confirmation: the reader test proves commit progress but misses checkpoint starvation.**  
   Hand-execution: R executes `BEGIN; SELECT …`; W commits a change successfully. R continues seeing its earlier snapshot until its transaction ends. That part of the proposal is correct. [SQLite transaction semantics](https://www.sqlite.org/lang_transaction.html#read_transactions_versus_write_transactions).

   Keep R open while W repeatedly commits: automatic checkpoints cannot finish past the pinned snapshot. “Every 1000 pages” is a trigger, not a size bound; automatic checkpoints are passive and may remain incomplete. [Checkpoint behavior](https://www.sqlite.org/c3ref/wal_checkpoint_v2.html), [automatic checkpoint configuration](https://www.sqlite.org/pragma.html#pragma_wal_autocheckpoint).

   A long-lived reporting transaction or retained cursor can therefore produce a growing WAL. The always-open supervisor does **not** cause this merely by being idle. Specify short reader lifetimes and how persistent checkpoint lag is detected; test checkpoint progress after releasing R, alongside successful commits while R remains open.

6. **Medium — §2 / Consequences: busy handling is attributed to the wrong operation and to machinery not present here.**  
   Hand-execution: A holds `BEGIN IMMEDIATE`; B enters `Store.transaction()`. B waits or fails at **`BEGIN IMMEDIATE`**, before the context manager yields—not ordinarily at `COMMIT` from another writer stealing its lock. The existing failed-commit rollback remains valuable, but it is not a retry policy. [SQLite’s transaction locking](https://www.sqlite.org/lang_transaction.html#deferred_immediate_and_exclusive_transactions).

   The current constructor hardcodes 5000 ms; [ADR-0017 §7.3](/E:/GitHub/scil/Leafi/docs/adr/0017-ai-led-study-session.md:348) specifies 250 ms plus asynchronous retries for study writes. Those retries are not established by the named opener code.

   Additionally, a new opener racing final-close cleanup or post-crash recovery can still receive `SQLITE_BUSY`. Define bounded startup/read handling rather than treating WAL reads as universally exempt. [SQLite’s WAL busy cases](https://www.sqlite.org/wal.html#sometimes_queries_return_sqlite_busy_in_wal_mode).

7. **Medium — [§§3–4 / Consequences](/E:/GitHub/scil/Leafi/docs/adr/0019-sqlite-wal-mode.md:17): “transient files” and “while Leafi runs” give the wrong crash-recovery boundary.**  
   Hand-execution: a transaction commits into a non-empty WAL, then the last process crashes before checkpointing. No process remains, but committed database state still lives in `-wal`. Reopening with the original files allows SQLite to recover; deleting the WAL or copying only `leafi.db` can discard those commits. `-shm` is rebuildable coordination state; `-wal` is not disposable. [WAL contents and recovery](https://www.sqlite.org/walformat.html).

   The blanket backup-API rule in §4 is good. Extend the operational rule explicitly to stopped-but-unclean databases, and include a crash/reopen confirmation that checks committed rows survive. “All processes stopped” must not become the criterion for safe manual copying.

8. **Low — [§5, Read-only openers](/E:/GitHub/scil/Leafi/docs/adr/0019-sqlite-wal-mode.md:19): the permission condition is incomplete.**  
   For ordinary `mode=ro`, SQLite documents **both readable `-wal` and `-shm` files**, or directory permission to create them. Existing `-shm` alone is insufficient. A script using a non-writable directory with missing/unreadable sidecars can fail despite satisfying the ADR’s wording. Test that permission case; the same-user writable-directory case should work. [SQLite read-only WAL requirements](https://www.sqlite.org/wal.html#read_only_databases).

The proposed rollback-mode failed-`COMMIT` regression is appropriate. The venv’s compiled defaults also confirm `FULL` synchronization and a 1000-page autocheckpoint threshold. I hand-executed the scenarios against the code and documentation; I did not run filesystem-mutating tests or edit files.
