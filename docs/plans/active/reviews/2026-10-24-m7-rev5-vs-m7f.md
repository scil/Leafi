## B. Conflicts that need the owner's decision

**B1 Per-turn `output_type` narrowing vs one schema per session (P4 vs M7 D6, O3).** P4 narrows `output_type` to the steps legal now, so the JSON schema differs between turns. M7 D6 and O3 rely on one byte-identical schema per (purpose, `PROMPT_VERSION`) so the vendor's compiled-schema cache (24 h) holds; each new schema costs a one-time compilation on its first request (vendor fact, D6 table), inside a 2 s practice moment. P5's legal set is a function of 12 step kinds and three state bits, so many distinct subsets can occur, each compiled once.
- Option 1 (recommended): one constant `Step` schema for `practice_turn`; legality checked by code after parsing (`legal_steps`), an illegal choice replaced by `next_default` and reported as `refused: <code>` (P4 already does this when narrowing fails). Cost: the model can propose illegal steps; the refusal codes tell it why.
- Option 2: narrow per turn as P4 says; accept compilation latency until the subsets are warm; measured in the prototype (M3).

**B2 Earlier conversation turns after `cloud.text` goes off mid-activity (P4 vs M7 D2/D3).** P4 re-renders every part from its leaves at every request, so Leafi's own parts (prompts, step results) are filtered correctly. The model's earlier **outputs** in the history (its `say` lines, hints, the plan) derive from the child's words and carry `derived_from_learner` (D2). If the learner's `cloud.text` is switched off mid-activity, those assistant turns may no longer leave, but removing an assistant turn breaks the conversation's structure.
- Option 1 (recommended): the conversation ends; the rest of the activity runs `next_default` (the `plan` planner's script), recorded `planner_used = plan`. Simple, and the case is rare (a settings change during practice).
- Option 2: replace each withheld assistant part with a fixed `[withheld]` text and continue; the model loses its own context.

**B3 The purpose `practice_turn` (P2/P4 vs ADR-0017 §5.1, M7 D15, the schema).** P4 adds a sixth purpose. `egress_log.purpose` has a `CHECK(purpose IN ('decide','generate','answer','judge','word','tts','media','catalog','ops'))` (`storage.py`), and each destination lists its purposes, so a new purpose is a migration (with migration 8, M7f) and an ADR-0017 §5.1 amendment; M7 D15 says "purposes stay ADR-0017's".
- Option 1 (recommended): add `practice_turn` as a purpose in migration 8 with its own route row (P4's `fast → standard`), the audit and egress log showing it plainly.
- Option 2: run turns as purpose `generate` with a `kind = practice_turn` tag and a route cell keyed by kind; no CHECK change, but `generate`'s routing and eligibility then depend on the kind.

**B4 Practice turns cannot escalate under rev 5's timing (P4 vs M7 D8).** P4: moment `feedback` 3 s (PC) − output reserve 1.0 s = 2.0 s; `fast` per call 1.5 s. Rev 5's walk compares the time left minus 0.3 s with `MIN_TIER_S[standard]` 2.0 s, so after a `fast` timeout (0.5 s left) or an invalid reply, `standard` is never tried: in practice the route is `fast` only, and a slow `fast` turn falls to `next_default`.
- Option 1 (recommended): accept `fast` only for `practice_turn` until M10 measures it; state it in the route table (honest about what runs).
- Option 2: give practice its own, longer moment (e.g. 5 s PC / 8 s camera) so `standard` can follow; the child waits longer between steps.

**Owner's answers (2026-10-24):** B2 option 1 (the conversation ends; the rest runs `next_default`); B3 option 1 (a new purpose `practice_turn` in migration 8, ADR-0017 §5.1 amended); B4 option 1 (`fast` only for `practice_turn` until M10). B1, after the explanation: neither option as written — **two fixed schemas**, `full` and `wrap-up` (`Focus`, `Attempt`, `Finish`, `Park`, `EndPractice`), switched by the time left and the turn budget; legality still checked by code; prototype measures the first-use compilation and whether a schema switch resets the prompt cache.
