# The system-of-record SQLite file runs in WAL mode when the SQLite library is fixed

Owner decisions 2026-10-22: "use WAL mode", from the research [`../research/2026-10-22-database-choice.md`](../research/2026-10-22-database-choice.md) (keep SQLite, ADR-0004 stands; do not adopt Postgres or ClickHouse); then, after the round-1 reviews found the WAL-reset bug, "WAL on by version (only SQLite ≥ 3.51.3), and replace the Python install's `sqlite3.dll`". Reviews: [`../plans/active/reviews/2026-10-22-adr-0019-codex.md`](../plans/active/reviews/2026-10-22-adr-0019-codex.md), [`…-claude.md`](../plans/active/reviews/2026-10-22-adr-0019-claude.md), [`…-code-plan-review.md`](../plans/active/reviews/2026-10-22-adr-0019-code-plan-review.md).

**Problem.** `data/leafi.db` runs in SQLite's default rollback journal (`journal_mode = delete`). Five kinds of process open it — the study session (`runner`), the supervisor (ADR-0016, from logon), and the `leafi` CLI commands — and in rollback mode a writer that is committing refuses new readers, and a reader that holds a read lock makes a writer's `COMMIT` wait and fail with `SQLITE_BUSY` after `busy_timeout` (code-plan-review pass 2, B3.2; the failed-`COMMIT` defect fixed in `508448b`). WAL (write-ahead log: changes are appended to a `-wal` file and copied into the database at a *checkpoint*) lets readers and the one writer proceed without blocking each other. But SQLite 3.7.0 through 3.51.2 carry the **WAL-reset bug** (`https://www.sqlite.org/wal.html` §11): two connections writing or checkpointing at the same instant can corrupt the database. The Python install here shipped SQLite 3.49.1.

**Decision.** `leafi.core.storage.Store` opens `leafi.db` in WAL only when the SQLite library loaded in the process is a fixed release; otherwise in rollback mode. Provenance: *adopted* — WAL, checkpoints, `journal_size_limit`, `secure_delete`, `VACUUM INTO` and the fixed-version list from SQLite's documentation (`wal.html`, `pragma.html`, `lang_vacuum.html`).

1. **The gate.** A library is fixed when its version is ≥ 3.51.3, or 3.50.7–3.50.x, or 3.44.6–3.44.x (the release and the two backports named in `wal.html` §11). `Store.__init__` decides on every open, after connecting and before migrating, because the gate follows the library of *this* process: a Python update can bring back an old `sqlite3.dll` (the next bullet), and the next open must then leave WAL.
   - Fixed: `PRAGMA journal_mode = WAL`; a no-op when the file is already in WAL; a new file is created in WAL.
   - Not fixed: if the file is in WAL, `PRAGMA journal_mode = DELETE` returns it to rollback mode and one warning is logged. If it cannot (another connection has the file open), the open **refuses** with `UnsafeSQLite`: an unfixed library never uses a WAL file (codex round 2, High).
   - Under a fixed library, the switch runs before `busy_timeout` is set, so it never waits: if it fails with `SQLITE_BUSY` / `SQLITE_LOCKED` (any other error is raised), the open continues in rollback mode, logs one warning, and the next open retries. `leafi doctor` reports the library version and the file's mode.
   - **The gate sees only its own process.** A process started before a DLL swap keeps the old library mapped, and a fixed opener can switch the file to WAL under it, which no check in this process can detect. Every Leafi process loads the same `sqlite3.dll` (§2), so this mix exists only between a swap and the restart of the processes that were running; the procedure in §2 closes that window.
   - `:memory:` databases are skipped (their mode is `memory`).
   - Tests pass `journal_mode=` to force a mode; production code never does.
2. **The fixed library on this PC.** Python's `sqlite3` module loads `DLLs\sqlite3.dll` from the interpreter's install (`D:\A\Scoop\apps\python312\current`). On 2026-10-22 it was replaced with sqlite.org's official `sqlite-dll-win-x64-3540100.zip` (SQLite 3.54.1, 1,450,919 bytes, SHA3-256 `c2d09c8b…f2daa4` matching the download page); the old DLL is kept beside it as `sqlite3.dll.3.49.1.bak`. A loaded DLL cannot be overwritten but can be renamed: rename the old one aside, copy the new one in, then **stop every Leafi process that was running (the supervisor too, `tasklist /m sqlite3.dll` lists them) before any process opens `leafi.db` with this code**, so none keeps the old library mapped when the file turns WAL. Verify with `.venv\Scripts\python -c "import sqlite3; print(sqlite3.sqlite_version)"` and the full suite. A `scoop update python312` reinstalls the stock DLL; the gate then turns WAL off and `leafi doctor` says so; repeat this step.
3. **Unchanged.** `synchronous` stays `FULL`, `busy_timeout` 5000 ms, `BEGIN IMMEDIATE` for writes, and the rollback of a failed `COMMIT` (`508448b`). ADR-0017 §7.3's 250 ms study-process timeout is not code yet; when it lands it sets its own timeout on its own Store, and this ADR does not change it. Automatic checkpoints stay at SQLite's default (1000 pages). In WAL, writer–writer contention surfaces at `BEGIN IMMEDIATE` (waiting up to `busy_timeout`), no longer at `COMMIT`. `SQLITE_BUSY_SNAPSHOT` (a read transaction that later tries to write fails at once, ignoring `busy_timeout`) cannot occur through `Store`, whose writes start with `BEGIN IMMEDIATE` or run in autocommit.
4. **Side-file size.** `PRAGMA journal_size_limit = 33554432` (32 MiB) on every connection: a `-wal` file that grew past it is cut back when the log restarts. It is not a cap: the log grows while any read snapshot pins it. `Store` holds no long read transactions (statements run in autocommit, `one()` / `all()` finish their cursors), so a pin lasts one query; the periodic checkpoint (§6) logs a warning each time a reader blocks it, which is how a stuck reader shows. `data/leafi.db-wal` and `data/leafi.db-shm` live under the gitignored `data/` (AGENTS.md boundary unchanged); WAL needs a local disk, which `data/` is.
5. **Migrations re-read the version inside the lock.** `migrate()` reads `user_version` *after* `BEGIN IMMEDIATE`, one step per transaction, so two processes opening an old file at once cannot both run the same step.
6. **Close and checkpoints.** `Store` is a context manager; the CLI commands use it, the study runner closes it in a `finally` spanning everything after the open, the supervisor in its shutdown `finally`. A process that dies before closing loses nothing committed: the next open recovers the `-wal`. `Store.checkpoint()` runs `PRAGMA wal_checkpoint(TRUNCATE)` and returns False when a reader blocked it; it runs at the end of a study session (a failure is logged, never masks the session's result) and after `forget`, and the supervisor retries it on its own short-lived connection every `CHECKS_EVERY_S` (900 s), off its event loop.
7. **Forgetting.** `PRAGMA secure_delete = ON` on every connection, so rows `forget` deletes are overwritten in the database pages; a *completed* `TRUNCATE` checkpoint empties the `-wal` that still holds their old pages. When the checkpoint is blocked, `leafi forget` says so and the supervisor's retry (§6) completes it. Content deleted before this ADR may survive in free space: the rollout runs `VACUUM` once. What `forget` deliberately keeps (correction text, encounters, summaries; ADR-0010 §9) is unchanged.
8. **Backups.** A copy of `leafi.db` alone can miss committed transactions still in `-wal`. `python -m leafi backup [--to <file>]` writes a consistent copy with `VACUUM INTO` (default `data/backups/leafi-<UTC timestamp>.db`), which also leaves out deleted-row remnants; any export or restore of the file (including ADR-0018 §7.2's migration backup) uses it, never a file copy. A backup keeps what was live when it was made: `leafi forget` lists the backups that predate it and tells the owner to delete them to forget there too; restoring one brings forgotten rows back. [`reliability.md`](../architecture/quality-attributes/reliability.md) says so.
9. **Read-only openers.** A `mode=ro` connection to a WAL file needs the `-wal` and `-shm` files readable, or the directory writable so SQLite can create them; ad-hoc scripts on this PC satisfy that. ADR-0018 §7.2's `migrate --learner` opens its Store after taking the `.users` lock, so the mode switch falls inside it.
10. **The habit track's `data/sessions.db`** (`agent/storage.py`, ADR-0004's separate store) is not changed.

**Consequences.** With the fixed library, the reader-side `SQLITE_BUSY` of pass 2 B3.2 disappears and a reader can no longer make a `COMMIT` fail; writers still take turns. Two side files appear in `data/` while Leafi runs, and copying the database by hand becomes unsafe — `leafi backup` replaces it. The Python install carries one hand-replaced file that a Python update reverts, after which Leafi silently falls back to rollback mode until the DLL is replaced again (`leafi doctor` shows it). Deletes cost a little more (`secure_delete`); the file is small.

**Confirmation.** `tests/test_storage.py`: the gate's version table (3.49.1 and 3.51.2 off; 3.44.6, 3.50.7, 3.51.3 on); a new store reports `wal` under a fixed library; an existing rollback file is switched on its next open; under an unfixed library (patched version) a WAL file is returned to `delete`, and refused with `UnsafeSQLite` while another connection holds it; a locked switch warns, the open succeeds and the next open retries; a reader holding an open read transaction does not block a write and its `COMMIT`; the failed-`COMMIT` regression test opens its store with `journal_mode="delete"` (rollback stays a production mode); `migrate()` from two stores racing on one old file runs each step once (red on the old `migrate()`); `forget` leaves no copy of a canary utterance in `leafi.db` or `-wal` (red without `secure_delete`); a pinned reader makes `checkpoint()` return False and the retry empties the `-wal`; `leafi backup` copies a row still in the `-wal`, and a later `forget` names the backup. The full suite passes. Round 2 (codex, increment): [`../plans/active/reviews/2026-10-22-adr-0019-round-2-codex.md`](../plans/active/reviews/2026-10-22-adr-0019-round-2-codex.md).
